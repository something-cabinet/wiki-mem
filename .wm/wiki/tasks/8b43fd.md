# wm-cli page link/update fails with NOT_FOUND from project root

**Severity:** P1 (tool reliability) — `page link`, `page update`, and `page delete` file checks are broken when run from the project root, which is the documented usage.

## Observed

```bash
cd <project-root>
wm-cli page link wiki:tasks:3db0ea wiki:specs:edge-type-pruning --edge-type implements
# Error: [NOT_FOUND] page not found: wiki:tasks:3db0ea
```

`page get` with the same ID succeeds. Running the identical link command with CWD = `.wm/wiki` succeeds.

## Root Cause

1. Graph build passes wiki-dir-relative paths to the parser: `graph/mod.rs` does `path.strip_prefix(wiki_dir)` then `parse_wiki_page(rel_path, ...)`.
2. `parse_wiki_page` stores that relative path verbatim: `meta.path = file_path.to_path_buf()` (`packages/wm-parser/src/lib.rs:316`) → `tasks/edge-type-pruning.md`.
3. `update_page_with_repo` (`apps/wm-core/src/page/services/page_update_builder_service.rs:46`) checks `repo.exists(meta.path)`; `FsPageRepo` (`packages/wm-page-repo/src/lib.rs`) resolves against process CWD.
4. From project root, `tasks/edge-type-pruning.md` doesn't exist (real path: `.wm/wiki/tasks/...`) → false NOT_FOUND.

`page get` works because it resolves via a different path (file lookup by ID, not `meta.path`).

## Fix Options

- **A (preferred):** store the wiki-root-anchored path in `meta.path` (pass the full path to `parse_wiki_page`, derive the ID separately via `path_to_id`), or
- **B:** make `update_page_with_repo` join `meta.path` onto the wiki dir before repo access.

Option A fixes all downstream consumers uniformly; check serialization of `GraphSnapshot` consumers (web UI may display `meta.path`).
